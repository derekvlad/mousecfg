# Архитектура

**Русский** · [English](en/architecture.md)

## Требование, из которого всё следует

Настройки мыши должны применяться **волатильно**: профили хранятся на хосте,
во встроенную память мыши не пишется ничего. Всё остальное — следствия.

## Слои

```
GUI (GTK4/libadwaita)   CLI (mousecfg)   трей (GTK3 + AppIndicator3)
        \                      /              /
         JSON-RPC через UNIX-сокет
                  |
          демон (systemd --user)
          ├── discovery    — поиск мышей в sysfs: HID++ и evdev-only
          ├── vendor       — вендорский канал YJX: чтение идентификации и дампов
          ├── profiles     — TOML-схема, хранилище, сопоставление
          ├── apply        — применение профиля, повтор при hotplug
          ├── appwatch     — активное приложение → выбор профиля
          ├── lighting     — волатильные эффекты подсветки
          └── evdev/uinput — ремап кнопок и макросы
                  |
          hidpp: transport → safeplane → guard → device
```

Протоколов два уровня. HID++ (`hidpp/`) даёт DPI, частоту опроса, режим и
подсветку. Мыши на закрытом вендорском протоколе (например, AJAZZ 2.4G)
сопровождаются только через evdev: `discovery.find_mice()` группирует hidraw-
интерфейсы одного устройства, отмечает протокол и находит `event`-узел.
Для `protocol = "evdev"` демон не открывает hidraw вовсе, а `engine.apply_profile(None, …)`
пропускает настройки протокола с понятным объяснением; профили, кнопки и
макросы продолжают работать.

`vendor/` — третий слой, только чтение. У мышей на контроллере YJX есть
отдельный HID-интерфейс (`usage page 0xFF01`, 64-байтные отчёты); он не
открывается демоном и не участвует в профилях. По явной команде
(`mousecfg vendor`) проект читает оттуда идентификацию, конфигурацию
(`parsers.py`: уровни DPI, активный уровень, частота опроса), заряд и
заводские коды, а также сырые ответы читающих команд; `mousecfg get` добавляет
прочитанное к карточке мыши. Демон раз в минуту читает заряд и показывает его
в `status`, трее и окне (значение сглаживается медианой: байт шумит на ±2%).

Перед каждым `os.write` кадр проверяет `vendor/guard.py`: по умолчанию
разрешены только read-команды. Запись в память (`0f/ae`, `09/a5`) доступна
лишь явной операции `mousecfg onboard` (CLI) или группе «Память мыши» в GUI
(те же RPC-методы `onboard-*`), всегда с `--allow-onboard-write`/подтверждением,
предупреждением при первом подключении и снимком до записи
(`vendor/snapshot.py`); `0d 00` (стирание памяти) не отправляется никогда.

`hidpp/guard.py` и `hidpp/safeplane.py` — ядро требования. Любая отправка
проходит через `SafePlane.send()`: сначала классификация команды
(`VOLATILE` / `PERSISTENT_CONSENTED` / `PERSISTENT`), потом запись в журнал,
и только потом `os.write` в hidraw. Неизвестная пара (фича, функция)
считается записью в память и не отправляется никогда.

Исключение — `send_by_index()`: индексы фич назначает само устройство,
поэтому во время перечисления (ROOT knock и FEATURE_SET) пара (feature id,
function) заранее неизвестна. Эти кадры могут только читать, их две.

## Почему не libratbag

`ratbagd` работает с моделью «профиль, записанный в устройство»: применение
настроек у него заканчивается записью в onboard-память. Проверено на
G102: `ratbagctl` показывает макрос, лежащий в самом устройстве. Поэтому
`libratbag` используется только как read-only ориентир при разборе протокола.

## Протокол

Реализован HID++ 2.0 напрямую: короткие (0x10) и длинные (0x11) кадры,
Software ID `0x09` (свободен от Solaar `0x0B`, OpenRGB `0x07`, G HUB `0x0D`),
индекс устройства `0xFF` для проводного USB. Ответы других клиентов и
нотификации устройства распознаются и пропускаются.

Опкоды сверялись с публичным поведением Solaar (в системе установлен
`1.1.20`) — как со справочником по протоколу, без копирования кода
(см. `docs/licensing.md`).

## Надёжность

* Поток обычных input-отчётов мыши (report id `0x01`, сотни кадров в
  секунду на 1000 Гц) фильтруется в транспорте: иначе он «съедает» окно
  ожидания ответа.
* `BUSY` от устройства — временный код, команда повторяется с паузой.
* Смена report rate приводит к переподключению USB: демон должен уметь
  терпеть исчезновение и появление устройства.
* Осиротевший UNIX-сокет после падения демона распознаётся: перед bind
  сервер проверяет, отвечает ли кто-нибудь на файле сокета.
* Если event-узел мыши ещё недоступен при подключении (ACL появляется с
  запозданием), демон периодически повторяет попытку поднять ремап кнопок,
  а не ждёт переподключения устройства.

## Режим устройства и согласие

Host mode — обязательное условие того, чтобы настройки с хоста вообще
применялись. Это единственная персистентная операция проекта (`0x8100/0x10`,
`persistent-consented`). Прошивка при этом не всегда помнит режим между
сессиями: G102 после перезагрузки возвращается в On-Board.

Согласие на переход пользователь даёт явно — `mousecfg mode
host --allow-onboard-switch`. Тогда ключ устройства записывается в
`~/.local/state/mousecfg/host-consent.json`, и при следующих подключениях
демон сам повторяет переход, если видит `onboard`. Это не новая запись:
пользователь уже согласился на эту операцию, а демон лишь приводит устройство
в состояние, без которого профили не работают. Без записи демон режим не
трогает (проверяется `tests/test_daemon_host_mode.py`). Отключить
автопереход можно ключом `--no-auto-host`.

## Демон

Демон — единственный, кто держит состояние «какая мышь какой профиль
использует». Клиенты (CLI, GUI) только просят:

| Метод | Что делает |
|---|---|
| `ping`, `status` | состояние демона, активное приложение, устройства |
| `list-devices`, `list-input-devices`, `list-macros` | инвентарь |
| `apply-profile` | применить профиль по id |
| `set-dpi`, `set-rate`, `set-lighting` | изменить одну настройку волатильно |
| `profile-activate`, `profile-next`, `profile-prev` | переключить профиль (трей и хоткеи) |
| `macro-upsert`, `macro-remove` | сохранить/удалить макрос (запись из GUI) |
| `set-remap` | включить/выключить ремап кнопок (трей) |
| `reload` | перечитать TOML-файлы и применить заново |
| `subscribe` | поток событий (`device-added`, `profile-applied`) |

Транспорт — JSON Lines через UNIX-сокет `$XDG_RUNTIME_DIR/mousecfg/daemon.sock`
с правами `0600`. D-Bus не используется: нужен минимум зависимостей, а
сокет в рантайм-каталоге пользователя уже ограничен правами доступа.

Профиль выбирается по «самому конкретному совпадению»: серийник важнее
приложения, приложение важнее общего профиля; порядок в файле разрешает
ничьи.

Ручной выбор (`profile-activate` из CLI/трея/хоткея) закрепляется в
`state.pinned_profile`. Пересчёт на каждой смене активного окна удерживает
закреплённый профиль, поэтому выбор не сбрасывается на первый профиль файла;
профиль с `match_apps` по-прежнему важнее закреплённого, а при уходе из его
приложения демон возвращает закреплённый. Закрепление переживает перезапуск
демона и снимается, если профиль удалили из файла.

## Кнопки и макросы

У G102 нет фичи divert (`REPROG_CONTROLS_V4`), поэтому единственный
работающий путь — evdev. Демон находит event-узел мыши, делает `EVIOCGRAB`
и ретранслирует движение через uinput, подменяя только те кнопки, что
попали в профиль. Макрос — данные TOML плюс интерпретатор на хосте:
повторное нажатие кнопки прерывает текущий макрос.

Ремап применяется только к кнопкам из профиля, поэтому `EVIOCGRAB` не
затрагивает обычную работу мыши.

Два следствия `EVIOCGRAB`, которые важно не забыть:

* После захвата нужно ретранслировать **все** события, включая непривязанные
  кнопки (`EV_KEY`): иначе левая и правая теряются и мышь «замерзает».
* Виртуальное устройство `mousecfg virtual input` должно быть доступно
  пользователю сессии. У uinput-узла нет `ID_SEAT`, поэтому общий механизм
  `uaccess` его не подхватывает — нужно отдельное правило
  `data/71-mousecfg-virtual.rules` с номером **до** `73-seat-late.rules`.
* Правила с тегом `uaccess` должны совпадать на всех действиях кроме
  `remove` (`ACTION!="remove"`), а не только на `add`. С systemd v258 ACL
  навешивает `systemd-udevd`, а logind лишь шлёт `change`-события; правило,
  ограниченное `add`, срабатывает при появлении устройства, но перестаёт
  совпадать на любом последующем `change` — и ACL на `/dev/input/event*`
  пропадает (кнопки и макросы «отваливаются» после перезагрузки). Это
  проверяет `tests/test_udev_rules.py`.
* Чтение событий идёт через `select` с таймаутом, а не через блокирующий
  `read_loop()`: иначе перехват не выключить, пока не придёт следующее
  событие (на неподвижной мыши — никогда).

## Подсветка

Эффект подсветки — такая же волатильная настройка, как DPI и report rate.
`guard` разрешает только волатильную запись `RGB_EFFECTS 0x8071/0x10` и
волатильный `setSwControl` (`0x8071/0x50`); персистентная запись NvConfig
(`0x8071/0x30`) запрещена, как и всё, что попадает в энергонезависимую
память. Подсветка хранится в профиле (`[profile.lighting]`) и применяется тем
же `engine.apply_profile()`.

Перед записью эффекта обязательно уходит `setSwControl` с полезной нагрузкой
`01 03 04` (`subfn=set`, `mode=3` — полный SW-контроль, `flags=0x04`):
прошивка серии LIGHTSYNC иначе продолжает рисовать цвет **onboard-профиля** и
игнорирует `setZoneEffect` — снаружи это выглядит как «подсветка не работает».
Так делает и Solaar (`rgb_power.SW_ACTIVE`) перед своими записями. Команда
волатильная: живёт в RAM до отключения мыши, в память мыши не пишет. Открытие
управления в этой серии не требует персистентной команды `ONBOARD_PROFILES
0x10 [02]` — проверено на железе.

Цвет в профиле — целое `0xRRGGBB`, но писать можно `#rrggbb`, `rrggbb` или
именем (`red`, `blue`). Яркость (0..100) превращается в байт `intensity`,
если эффект его знает; у `static` яркость притемняет сам цвет, потому что
отдельного параметра интенсивности у него нет.

## Трей и глобальные хоткеи

Трей — отдельный процесс GTK3 + AppIndicator3 (`mousecfg-tray`), потому что
AppIndicator3 несовместим с GTK4/libadwaita в одном процессе. Устройство он
не открывает: все действия идут через тот же JSON-RPC.

Автозапуск трея — через `~/.config/autostart` и
`systemd-xdg-autostart-generator`. Тонкость: генератор молча отбрасывает
`.desktop`, если исполняемый файл из `Exec=` не найден в `PATH` менеджера
systemd, а `~/.local/bin` в этот `PATH` не входит. С `Exec=mousecfg-tray` трей
поэтому не запускался бы вовсе (юнит не генерируется). Установщик подставляет
абсолютный путь к `mousecfg-tray` в `Exec=` — иначе иконки в панели нет.

Смена профиля по глобальному хоткею сделана через портал
`org.freedesktop.portal.GlobalShortcuts`. У портала жёсткое требование: app
id выводится из имени systemd-юнита (cgroup), вида
`app-<app-id>-<суффикс>.scope`. Поэтому трей при запуске сам заходит в scope
`app-io.github.mousecfg.MouseCfg-tray.scope` через `systemd-run --user
--scope`. Ответы портала асинхронные (`Response`), нажатия приходят сигналом
`Activated`.

Портал есть не везде. На niri и других wlroots-композиторах единственный
бэкенд, объявляющий `GlobalShortcuts`, — GNOME; под niri он не открывает
сервисный Wayland-канал и вместо диалога показывает никогда не закрывающиеся
окна «Add Keyboard Shortcuts». Поэтому `hotkeys.portal_supported()` распознаёт
такой композитор, и трей портал не трогает. Хоткей тогда вешает сам
композитор: `mousecfg keybinds` печатает готовый блок `binds` для niri (и
умеет дописать его в конфиг с бэкапом), а действие вызывает
`mousecfg profile next`/`next --prev` — те же RPC, что и у портала.
