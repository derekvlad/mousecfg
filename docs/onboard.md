# Запись в память мыши (onboard)

**Русский** · [English](en/onboard.md)

Мышь, где профили живут на хосте (см. `docs/architecture.md`), по умолчанию
не пишет в память устройства. Но у некоторых мышей (AJAZZ 2.4G на контроллере
YJX) есть собственная память, куда можно сохранить настройки так, чтобы они
пережили отключение и работали на любом компьютере без демона.

Для этого есть отдельные команды `mousecfg onboard`. **Это единственное место,
где проект меняет энергонезависимую память мыши.** Профили демона её не трогают
никогда.

## Коротко: что можно

```sh
mousecfg onboard show                     # прочитать текущие настройки
mousecfg onboard backup                   # снимок в ~/.config/mousecfg/backups
mousecfg onboard apply --dpi 1600 --allow-onboard-write
mousecfg onboard apply --rate 1000Hz --allow-onboard-write
mousecfg onboard restore --allow-onboard-write    # вернуть последний снимок
```

В GUI то же самое — группа **«Память мыши»**: выбор уровня DPI, значение,
«Снимок», «Вернуть снимок», «Записать DPI в мышь».

## Что именно сохраняется в мышь

Для AJAZZ 2.4G (`a8a5:2255`, диалект `mkespn`):

| Поле | Как задать |
|---|---|
| Уровни DPI (до 6) и активный уровень | `onboard apply --dpi N --dpi-level K` (K = 0..5) |
| Частота опроса | `onboard apply --rate 1000Hz` (или `1ms`, или код 1..4) |
| Режим подсветки | `onboard apply --light-mode N` |
| LOD, сон, отклик, high-speed | `--lod`, `--sleep-light`, `--key-respond`, `--highspeed` |

Значение пишется **поверх живого чтения**: служебные и неизвестные байты
(включая тот, что меняется сам) остаются как есть. Запись раскладки кнопок
(`09/a5`) в коде тоже есть, но пока не подключена к CLI/GUI: раскладку кнопок
эта мышь **не отдаёт на чтение**, поэтому откатить её нашим `restore` нельзя —
только веб-конфигуратором. Поэтому по умолчанию мы этого не делаем.

## Почему это безопасно

1. **Снимок до записи.** Перед каждой записью снимается полный снимок
   конфигурации в `~/.config/mousecfg/backups/` (JSON с полным кадром и
   отпечатком sha256). Откат — `mousecfg onboard restore`.
2. **Согласие.** Без флага `--allow-onboard-write` (в GUI — без подтверждения
   предупреждения) запись не выполняется никогда. При первом обращении
   показывается предупреждение с рисками; согласие запоминается по устройству
   (`~/.config/mousecfg/onboard-consent.json`).
3. **Узкий белый список.** Отправляются только кадры `0f/ae` (конфигурация) и
   `09/a5` (кнопки, если включено). Команда `0d/00`, которая с непустым телом
   **стирает** участок памяти, не отправляется никогда
   (`mousecfg judge` перечисляет политику).
4. **Демон не пишет.** Профили остаются волатильными; запись доступна только
   по явной команде. Демон лишь помогает GUI теми же RPC-методами.

## Если что-то пошло не так

Порядок восстановления:

1. `mousecfg onboard restore --allow-onboard-write` — записать последний снимок.
2. Веб-конфигуратор AJAZZ (вкладка **Onboard configuration**) → **Import**
   файла снимка (`~/.config/mousecfg/backups/…json`) или **Reset to default**.
3. Штатное ПО / веб-конфигуратор с «Reset to default».

Раскладка кнопок через наш `restore` не восстанавливается (см. выше) — только
пункты 2–3.

## Что осталось неизвестным

Протокол разобран сообществом и веб-инструментом AJAZZ, а не документирован
вендором. Не расшифрованы: хвостовые байты конфигурации (LOD/датчик — пишутся
как есть, не трактуются), назначение заводских кодов, полный каталог моделей.
Смещения полей сверены с живым ответом на AJAZZ 2.4G — на других моделях
семейства они могут отличаться, поэтому сначала стоит сделать снимок.
